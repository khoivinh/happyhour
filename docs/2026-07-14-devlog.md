# 2026-07-14 — Alt header: logo + hero as one unit, sticky rule

Branch: `alt-header` (not merged — `main` keeps the current layout deployed).
Spec: `2026-07-14-happyhour-edits.md`. Figma: `329:3241` (top), `329:3521` (scrolled).

## Why

The page read as two stacked headers — the branding bar (`sticky top-0` with a `border-b`)
and the hero clock. On scroll, the header's rule and the city-list's rule both parked near
the top of the viewport, showing two horizontal rules a few pixels apart.

The fix treats the logo and hero as one unit: the logo bar loses its rule and scrolls away;
the hero's time display shrinks continuously; the rule *beneath the hero* rides up and locks
to the top. One rule, never two.

## Decisions

**The drawer toggle was never actually pinned.** The spec said it "MUST stay in the exact same
position" and called it a hard-won constraint. It wasn't: the button sat in the header's
`items-center` row, so as the wordmark shrank on scroll (52 → 37px) with `padding-top` fixed at
32px, its center **rose ~7.5px**. The sidebar compensated by re-measuring
`toggleRef.getBoundingClientRect()` every scroll frame and threading it through `sidebarTop`.
What *was* hard-won is the **horizontal** contract (old `world-clock.tsx:172-176`): the header's
`pr-[10px]` aligned the closed-state toggle with the sidebar's open-state close icon.

Pinning it properly *removed* machinery. The toggle now lives in the fixed menu layer that already
shared the sidebar's `mx-auto max-w-4xl` column, so the alignment is structural rather than two
padding values that happen to match — and `sidebarTop` state, `toggleRef`, and the per-frame
`getBoundingClientRect` are all gone.

**Figma's `pr-[20px]` is the value the old code comment explicitly forbade.** Frame `329:3241`
puts the toggle 20px inside the content column; the code used 10px *because* 10px is what aligns
it with the sidebar close icon. Following Figma would have shifted the closed-state icon 10px left
of the open-state one — the exact regression the spec forbids. **Kept 10px horizontally, took
Figma's 45px vertically.** This is the one deliberate departure from the frame.

**The rule is not glued to the hero — it travels.** Figma default puts the rule at y=208 with the
hero ending at 144 (64px gap); the sticky frame has both at 114. So the gap collapses 64 → 0 as
you scroll. Implemented as an interpolated `padding-bottom` on the sticky block, not a static border.

**JS writes one number.** The scroll handler sets `--hero-ratio` (0→1) on `documentElement`;
every size *and the breakpoint* live in `index.css`. This kept `DigitalClock` dumb, stayed off the
render path (no re-render per frame, matching the existing imperative style), and deleted the JS
`window.innerWidth < 500` breakpoint in favor of a media query.

# 2026-07-14 (round 2) — feedback fixes

Spec: `2026-07-14-happyhour-edits-2158.md`. Still on `alt-header`; `main` untouched.

## The headline: the shudder was NOT what I diagnosed

Round 1 flagged a "document-height feedback loop" — the hero shrinking by 94px shortens the page,
which clamps `scrollY`, which lowers `--hero-ratio`, which regrows the hero. That was real, and
`min-h-[calc(100lvh+120px)]` on `<main>` fixes it (a scroll runway that decouples document height
from hero height). **But it was not the actual cause.** After that fix, `scrollHeight` was provably
constant at 1020 and `maxScroll` a constant 120 — and the ratio *still* stalled, oscillating
between scrollY 67 and 68 forever.

The real culprit is **browser scroll anchoring**. Chrome and Firefox watch for content above the
viewport changing size and nudge `scrollTop` to keep the content below visually still. But
`scrollTop` is precisely what drives `--hero-ratio`, so every nudge resized the hero, which
triggered another nudge. A closed loop, entirely inside the browser's own compensation machinery.

```css
html { overflow-anchor: none; }   /* index.css */
```

Safari implements no scroll anchoring at all, which is why this never reproduced there.

Both fixes are needed: the runway guarantees `SCROLL_RANGE` is always *reachable*; `overflow-anchor`
stops the browser fighting the shrink on the way there.

| repro (1091×900, one tile row) | before | after |
|---|---|---|
| `--hero-ratio` at bottom | 0.56, oscillating | **1.00, steady** |
| `scrollY` at bottom | 67↔68 forever | **120** |
| `scrollHeight` across scroll | varied | **constant (1020)** |

## Decisions

**Icon alignment forced a choice.** The icon is pinned, so aligning it with the sticky city name
also moves it at scroll-top. Measured the ink tops rather than guessing: the wordmark's SVG
`getBBox().y` is **0** (its ink fills the viewBox — the old "glyphs sit low" comment refers to the
round mark's optical centering, not a vertical offset), and the sticky city's ink top is **22.28px**.
Since the nameplate's `pt-[9px]` doesn't scale, `pt-[13px]` on the logo bar puts the wordmark's ink
top at 22px too. So a single `top: 22px` aligns the icon with the top of the leftmost text in *both*
states, at *both* breakpoints. Deliberate departure from Figma `329:3242`'s 29px top padding
(Khoi chose this over keeping Figma's padding and letting the icon float).

## Verification (measured)

- Shudder repro: ratio reaches exactly 1, `scrollHeight` constant, at the reported 1091×900.
- Toggle still pinned: identical top/right at scrollY 0/60/120/400/2000, all breakpoints.
- 6 deliberate near-miss taps around the icon in the sticky state: editor opened **0** times.
- Editing while sticky: OK button right edge 294px vs icon left edge 316px (mobile) — clears.
- Sticky zone/temp computes to exactly 12px.
- Geo notice in the footer, absent from the hero; `/about` `/privacy` `/support` `/nope` all render
  with no page errors and correctly omit it.
- Sticky bg opaque in all four themes. `tsc --noEmit` + `npm run build` clean.

## Note

`scrollHeight` still varies by ~94px on viewports where content exceeds the min-height (e.g. 620px
tall). That is expected and harmless: there `maxScroll` (253px) far exceeds `SCROLL_RANGE` (120px),
so no clamp fires inside the live range, and with anchoring off there's no loop.

## One straggler, caught at the merge

Round 1 gave the ancillary pages (About / Privacy / Support / 404) a header matching the new home
logo bar, and wrote a comment on each saying so — *"navigating between home and an ancillary page at
scroll-top produces no jump."* Round 2 then retuned **only** the home bar (`pt-[29px]` → `pt-[13px]`,
to land the wordmark's ink top on the drawer icon's 22px). The ancillary headers were left behind.

So the comment was asserting an invariant the code no longer held: a **16px jump** on every
navigation between home and a content page — the exact regression the parity was introduced to
prevent. Fixed by taking the ancillary headers to `pt-[13px]` too (`b2daa7f`).

Measured rather than computed, since the wordmark scales 0.73 below 500px and the nameplate's
`pt-[9px]` doesn't:

| page | wordmark ink top @1091px | @375px |
|---|---|---|
| `/` `/about` `/privacy` `/support` `/nope` | **22px** (all five) | **22px** (all five) |

Which is the same 22px the drawer icon is pinned to — so the icon, the wordmark, and the sticky city
name all share one baseline, on every route.

**Lesson worth keeping:** a comment that promises two files agree is not a mechanism that makes them
agree. Round 2 changed one side of a two-sided invariant and nothing failed — no test, no type error,
just a silently false comment. If this parity is load-bearing (it is — it's now been re-established
twice, on 2026-04-25 and again here), it wants a shared constant or a shared header component rather
than a third round of the same fix.
