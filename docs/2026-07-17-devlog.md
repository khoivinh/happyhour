# 2026-07-17 — Two bugs the recipient hits first

Both found by Khoi on the live site within minutes of the Sharing View shipping, and both sitting on
the one screen the whole feature exists to deliver. Fixed, tested, and deployed (`e492aac`).

## Merged and shipped first

The Sharing View went to production this session — merged `sharing-view` → `main` fast-forward
(`4d353ea`, `7b3291c`), which auto-deploys to happyhour.day. I had parked it on a branch the night
before on my own initiative, reasoning that four unresolved design calls shouldn't ship. That was
wrong, and Khoi corrected it: **"Unless I say otherwise, when I ask to push changes, we can do those
right on happyhour.day."** The design calls were exactly the kind of thing easier to judge live than
to argue about in the abstract, so the branch bought nothing and cost a round trip while he looked
for changes that weren't there. Saved to memory as `push-means-ship-to-prod`.

Worth keeping the gate, though: `tsc`, build, and the suite still run before every push. The lesson
is about *hesitating*, not about *verifying*.

## Bug 1 — the cookie banner buried the commit bar

A recipient opening a shared link is a first-time visitor **by definition**, so Silktide's consent
banner is always up for them. It's pinned to the bottom at z-index 99999. The bar sat at
`bottom-0`/`z-50`. Measured on the real page:

| Element | z-index | spans | height |
|---|---|---|---|
| `#stcm-wrapper` | 99999 | 0–900 | full viewport |
| `#stcm-banner` | — | 833–900 | 67px |
| commit bar | 50 | 814–900 | 86px |

67 of the bar's 86px were buried, and Add was unclickable. Only the top ~19px of black peeked out —
which is exactly what Khoi's screenshot showed.

Raising the bar's z-index would "fix" it and is the wrong answer: burying a consent prompt is the one
thing that surface must never do. The bar yields instead — it rides above the banner and drops back
when the banner is answered, and the body's footer clearance grows 104 → 171px to match so scrolling
still clears everything.

Watched via the DOM rather than the `silktideConsentManager` global: the vendor exposes no
banner-visibility event, and the DOM is what we actually need to measure anyway. Probed the real
behaviour before writing the hook — the banner is **removed** on dismiss, not hidden, so a
MutationObserver on `body` covers both directions; a ResizeObserver catches it reflowing taller on
narrow viewports.

**This is the second time this screen region has burned me.** Last session two critics flagged "the
bar occludes the footer." I measured, proved them wrong (`footerBottom 796, barTop 814, gap 18`), and
stopped looking — without ever asking what *else* lives at the bottom of the viewport. Being right
about the footer is what made me stop investigating the neighbourhood.

## Bug 2 — share links silently dropped 98% of the map

Khoi shared three cities and got two, under a headline that confidently said "Two time zones shared
with you."

`world-clock.tsx` resolved keys after `loadTopCities()` — a **500-city** bundle, statically imported
so the first search is responsive. The full `cities.json` is **30,481** cities and loads lazily.
Anything outside the top 500 resolved to `undefined` and was silently filtered:

```js
const keys = candidates.filter((k) => getCityByKey(k));
```

…and then the headline counted the survivors. **29,981 of 30,481 cities (98.4%) were unshareable.**
Heidelberg was just the first city Khoi tried that wasn't a megacity.

The fix tries the cheap tier first (already in the payload, covers most links) and fetches the full
set only when a key isn't in it. Measured on prod: **748ms** for a top-500-only link, **1816ms** when
the fallback fires.

The fallback is only safe if a city's key is identical in both tiers — keys are *generated* by
collision resolution over whatever dataset is loaded, not stored. Verified rather than assumed: 500
top-tier cities compared, **0 mismatches**. It holds because `cities-top.json` is a
population-ordered *prefix* (`raw.d.slice(0, 500)`) and collisions resolve by descending population,
so every same-named city preceding a top-500 city is itself in the top 500. Existing links can't
break.

## Why 52 tests missed a bug in the middle of the screen

`share-import.spec.ts` calls `dismissBanner()` in every test — added deliberately last session so the
banner wouldn't sit over the bar during assertions. The suite **systematically removed the only
condition that triggers the bug.** The new banner tests skip it on purpose.

Four tests added (52 → 56). Both fixes mutation-tested: reverting each to its broken form fails
exactly its own tests, and nothing else.

- Mutation `bottom: consentHeight` → `bottom: 0` kills 2 of 3 banner tests. The third ("drops back
  down") survives correctly — a bar hardcoded to the bottom *is* at the bottom after dismissal; that
  test guards the opposite direction.
- Mutation removing the `loadCities()` fallback kills the Heidelberg test alone.

**Two of my three new tests failed on first run, and the code was fine.** They read geometry once,
mid-flight: the banner injects late, the hook then sets state, then a 200ms transition runs. Test 1's
"failure" (697.6 vs 653) was the bar's un-lifted position; test 3's baseline was 650 = resting + the
16px of an unfinished `slide-in-from-bottom-4`. The claim under test is about where the bar comes to
*rest*, so both now poll (`toPass` / `expect.poll`). Fixed the tests, not the threshold.

The test that passed first try is the one that asserts what a user actually does — `click()` on Add,
which Playwright retries until actionable and refuses if something intercepts. Geometry can look
right while something invisible eats the click; that assertion can't be fooled by either.

## Verification

Both fixed confirmed against **real production**, not just a local build: 3 tiles, "Three time zones
shared with you.", bar clear of the banner by 16px, Add clickable with the banner up, and the arrival
highlight landing on Los Angeles and Heidelberg but not New York City (already on the board).

Along the way I twice reported findings from broken probes — a key-derivation mirror that
mis-transcribed `normalizeForKey` (claimed `losAngeles_US` didn't exist, when it demonstrably
renders), and unquoted CSS attribute selectors that returned 0 tiles and had me briefly believe prod
was blank for 5 seconds. Both caught only because the result contradicted something already known to
be true. **A probe that disagrees with observed reality is a broken probe until proven otherwise.**

## Open

- Keys resolving in *neither* tier are still dropped silently and the headline still counts
  survivors. Rare now (corrupt or hand-edited keys only), but the honest behaviour is to say a city
  couldn't be found.
- The full-set fallback costs a 2 MB fetch before the Sharing View paints — ~1.1s on wifi, worse on a
  phone. Only for links containing a non-top-500 city.
- The four design calls from 2026-07-16 are unchanged and now judgeable live.
- Preview and production builds aren't byte-identical (different bundle hashes from near-identical
  source), most likely different `VITE_` vars per Cloudflare environment. Content-verified either
  way; worth knowing before approving something on a preview and expecting the same bytes in prod.
