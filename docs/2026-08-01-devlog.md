# 2026-08-01 — Clearing the iCloud husk left behind by the relocation

No application code changed. This was a repo-status check that turned into a filesystem problem: the
session opened in the **old** iCloud path, and the empty folder still sitting there refused to be
deleted.

Sequel to `2026-07-25-devlog.md` (iCloud stalling the build) and to the 2026-08-01 relocation of all
ten git repos into `~/Developer/`.

## 1. The status check: the repo was fine, the directory wasn't

The session's working directory was
`iCloud/…/Claude Projects/Code/Happyhour` — which, post-relocation, is **not a git repository**.
`git rev-parse` returned `fatal: not a git repository`.

The real repo was clean:

| Check | Result |
|---|---|
| Location | `~/Developer/Happyhour` |
| Branch | `main` → `origin/main` |
| Working tree | Clean |
| Local HEAD | `0f9d563` |
| Live `origin/main` (`git ls-remote`) | `0f9d563` — identical |

**The misleading part:** the SessionStart snapshot listed six dirty paths (`STATUS.md`,
`docs/2026-07-25-devlog.md`, three untracked planning docs). None of that was real work in progress —
it was a stale reading of the pre-relocation location. The iCloud folder contained **zero files with
bytes**; its only content was an empty `.wrangler/` directory.

This is worth flagging as a general hazard: a session launched from a relocated path reports repo
state for a repo that isn't there.

## 2. The husk that wouldn't die

`rmdir` succeeded, and the folder came back ~10 seconds later with `.wrangler` inside it.

A 2-minute delete-and-watch loop, re-deleting on every tick:

```
24 present   16 gone   9 successful re-deletes
```

It never converged. Reappearance interval was ~3–12 seconds, indefinitely.

### What it wasn't

- **Not a stray dev server.** No `wrangler` or `vite` in the process list; the only `node` processes
  were MCP servers and Adobe CC.
- **Not Claude Code re-creating its own cwd.** The harness `cd`s the shell to the session's working
  directory on every Bash call — but the resurrections happened *mid-loop, inside a single
  invocation*, with no harness `cd` in between. And a `cd` cannot create `.wrangler`.
- **Nothing was holding it open.** `lsof -a -d cwd` showed only my own `zsh` and its children, and
  the directory carried a **fresh inode** each time — genuinely re-created, not merely un-deleted.

### What it was

`brctl status` stamped `last-sync` at the same second as the delete. The best-supported explanation
is that **a POSIX unlink bypasses the iCloud file provider**: the server-side copy is never told the
item was removed, so it syncs straight back down. (Inferred from timing and the elimination above —
not confirmed with `fs_usage`, which needs root.)

### The fix

Route the delete through Finder so it goes through the provider:

```bash
osascript -e 'tell application "Finder" to delete POSIX file "/absolute/path"'
```

| | `rmdir` | Finder / osascript |
|---|---|---|
| Longest survival | ~12 s | 100+ s, still gone |
| Reappearances | 24 in 2 min | 0 |

The folder now sits in `~/Library/Mobile Documents/.Trash/Happyhour` — recoverable, and it stayed
deleted through the full verification poll.

## Decisions

- **Verify deletes on iCloud paths by polling, not by exit code.** `rmdir` returned 0 every time it
  ran, while losing the race. Exit status says nothing about whether the item stays gone.
- **Left the sibling husks alone.** `Code/Bad Company` and `Code/Postcredits` are the same kind of
  empty leftover but weren't in scope. `Code/Design Craft` and `Code/Shotglass` stay by design —
  Design Craft is `@import`ed by the global `CLAUDE.md`, Shotglass keeps companion docs in iCloud.
- **Recorded the gotcha in project memory** rather than only here, since it applies to every repo
  moved out of iCloud, not just this one.
