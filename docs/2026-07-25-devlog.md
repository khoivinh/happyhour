# 2026-07-25 — Sync the repo, and unblock the build from iCloud

No application code changed this session. It started as `git pull` plus "set up Playwright," and both
turned out to be blocked by the same underlying cause: **this repo lives in iCloud Drive, and iCloud
had gotten ahead of (and then inside) the toolchain.**

## 1. The pull: 35 commits behind, blocked by identical files

`git pull` aborted — 5 tracked files modified, ~25 untracked files (devlogs, `functions/`, `tests/`,
`playwright.config.ts`) colliding with incoming ones.

The files were **byte-identical to `origin/main`**. Verified all 24 blocking paths with
`git show origin/main:<path> | diff -q - <path>` before touching anything; every one came back SAME.

**Diagnosis:** iCloud had synced the *working-tree files* from another machine ahead of the `.git`
metadata, so the content was already present while `HEAD` still sat at `57a8c7d`. This is the
signature to look for — git reporting local "changes" that are indistinguishable from the remote.

Resolution: backed up all 33 modified/untracked files to a scratchpad, reverted the 5 tracked files,
removed the untracked blockers, pulled. Fast-forward `57a8c7d..34a464b`, 59 files, clean tree.
Nothing was lost — nothing differed from what the pull brought in.

## 2. The build: 0% CPU, forever

`npm test` timed out at 120s waiting on `config.webServer`. Then `npm run build` — which the
`playwright.config.ts` comment says costs ~3s — **ran past 10 minutes**.

The tell was in `ps`: the vite process held 545MB resident at **0.0% CPU**. Not compiling — blocked
on I/O.

```
find node_modules -type f -flags +dataless | wc -l
→ 7569        (of 9761 total files)
```

**7,569 of 9,761 dependency files were iCloud "dataless" placeholders.** Every module resolution
blocked while iCloud fetched that one file over the network. The build wasn't slow, it was stalled.

Two things this explains:
- **Why the earlier `npm install` didn't fix it.** It reported "added 1 package, changed 1 package"
  — npm saw an intact tree with correct metadata and never re-materialized the placeholder files.
- **Why `.gitignore` already had the answer.** It carries the line
  `node_modules.nosync/  # Real dependency dir; iCloud skips any path ending in .nosync`. A previous
  session had established this convention; it had since reverted to a plain `node_modules` — most
  likely an `npm install` run after the folder synced to another machine.

Also found: `node_modules 2/`, a **139MB iCloud conflict copy** (gitignored, pure junk).

## 3. The fix — restore the `.nosync` convention

```bash
rm -rf node_modules "node_modules 2"
mkdir node_modules.nosync
ln -s node_modules.nosync node_modules
npm install
```

macOS iCloud skips any path ending in `.nosync`, so the real dependency tree becomes local-only —
never uploaded, never evicted. `node_modules` stays a relative symlink, so every tool resolves it
normally and nothing else in the project needs to know.

| Metric | Before | After |
|---|---|---|
| Evicted files in `node_modules` | 7,569 of 9,761 | **0** |
| `npm install` | — | 2.9s |
| `vite build` | >10 min, never completed | **2.94s** |
| `npm test` | timed out at 120s | **75 passed, 21.4s** |

Build time landing at 2.94s matches the "~3s" the config comment predicted — good evidence the
environment is now what the test config was written against.

## 4. Playwright

- Deps installed (`@playwright/test` ^1.61.1, already in `package.json` from the pull).
- `npx playwright install chromium` → Chrome for Testing 149.0.7827.55 + headless shell, into
  `~/Library/Caches/ms-playwright`. **Outside iCloud**, so the browser binaries were never part of
  the problem and don't need `.nosync` treatment.
- Config is chromium-only, so no other browsers were fetched.
- Full suite: **75 passed in 21.4s.**

Both `node_modules` and `node_modules.nosync/` are already gitignored — `git status` is clean and
this session has nothing to commit.

## Decisions

- **Verified byte-equality before discarding local changes**, rather than reaching for
  `git reset --hard` / `git clean -fd` on sight. In an iCloud-backed repo, "local modifications" are
  often just sync lag, but they can equally be real uncommitted work — the diff check is what
  distinguishes them.
- **Chose the `.nosync` symlink over a plain reinstall.** A plain reinstall would have unblocked
  today and re-broken as soon as iCloud re-evicted the files, while also re-uploading 37MB of
  dependencies on every install.

## Follow-ups

- **This will recur on the other machine.** The `.nosync` symlink is itself a local, unsynced
  arrangement — whichever machine currently has a plain `node_modules` will hit the same hang. The
  same four commands fix it there.
- `npm audit` reports 8 vulnerabilities (1 critical, 5 high) in the dependency tree. Pre-existing,
  untouched, not investigated.
- Worth considering: the same `.nosync` treatment for any other iCloud-hosted JS project in this
  workspace (CardFC and Movietalk both carry a `node_modules`).

# 2026-07-25 (part 2) — The open sidebar now fills the viewport

**Shipped + live — `460b73d`, pushed straight to `main` (Pages auto-deploys).**

Khoi: *"it feels awkward that it only extends about 80% of the height of the viewport."* It did —
and the reason turned out to be a leftover, not a decision.

## The 92% was vestigial

`sidebar.tsx` had `height: calc(92dvh - 42px)` against a `top` of 14px. On an 800px viewport that's
a **14px gap at the top and a 92px gap at the bottom** — the asymmetry Khoi was reacting to.

| Date | Change | Reason |
|---|---|---|
| 2026-03-21 | Original spec | "full viewport height less padding ~28px on the top and the bottom" |
| 2026-03-25 (`f1b7def`) | `100vh` → `80dvh` | `100vh` on mobile Safari counts the area *behind* browser chrome, so the drawer ran below the fold |
| 2026-03-25 (`3f79763`) | `80dvh` → `92dvh` | 80 over-corrected and left the panel visibly short |

**The mobile bug was fixed by the unit change (`vh` → `dvh`), not by the percentage.** `dvh` already
excludes the address bar — `docs/PRD.md:183` says exactly that, and uses it to justify why the
sidebar "never extends below fold." Once the unit changed, the 8% haircut was belt-and-braces that
nobody went back to remove. So this is less a new decision than a return to the 2026-03-21 spec.

## The change

One line, `client/src/components/sidebar.tsx`:

```diff
- height: `calc(92dvh - ${topOffset - 18 + 28}px)`,
+ height: `calc(100dvh - ${(topOffset - 18) * 2}px)`,
```

Derived as `(topOffset - 18) * 2` rather than a hardcoded `28px`: `topOffset - 18` is already the
top-gap expression on the line directly above, so the symmetry stays correct by construction if
`TOGGLE_TOP` is ever raised. Left a comment saying why it's `100dvh` and not a percentage, so it
doesn't get "re-fixed" back to `92dvh` by someone reading only the old commit messages.

## What this deliberately did not touch

`docs/PRD.md:242-246` defines the interlocked system — `TOGGLE_TOP`, `LogoBar`'s top padding,
`.hero-clock`'s `padding-top`, and the sidebar's `topOffset − 18` — with the standing warning
"change one, re-measure all four." Parity there has silently broken twice before.

That invariant governs the panel's **top edge**. This change moves only the bottom edge: `top` stays
`topOffset - 18`, the `−18` / `pt-[18px]` pair is untouched, `TOGGLE_TOP` is untouched. Verified by
measurement rather than by reasoning — see below.

## Verification

`tsc --noEmit` and `build` clean. **75 Playwright tests pass, unchanged** — no existing test asserts
the panel's geometry, so a failure would have meant something moved that shouldn't have.

Measured with a throwaway Playwright harness (deleted after the run) at three viewports:

| Viewport | Toggle top | Panel top gap | Height | Bottom gap | % of viewport |
|---|---|---|---|---|---|
| 1280×800 | 32.00 | 14.00 | 772.00 | 14.00 | 96.5% (was ~87%) |
| 375×667 | 32.00 | 14.00 | 639.00 | 14.00 | 95.8% |
| 375×400 | 32.00 | 14.00 | 372.00 | 14.00 | 93.0% |

Symmetric at every size, and `toggle top = 32.00` confirms the close-icon alignment — the
non-negotiable regression — is intact.

The `sidebar-open` / `sidebar-close` `clip-path` keyframes (`index.css:357-386`) are anchored
top-right via `calc(100% - 48px)`, so they adapt to the new height and needed no change.

## Known cosmetic interaction — the cookie banner

The panel's bottom edge now sits at `100dvh - 14px`, which is **behind the Silktide cookie banner**
while that banner is up. Previously the panel stopped short enough to clear it. The overlap is
purely cosmetic — panel content is top-aligned, so only empty dark space and the bottom rounded
corners are covered, and it ends as soon as the banner is answered. Not fixed; flagged for Khoi.

There is precedent for treating this as worth fixing: the commit bar already dodges the banner
(`tests/share-import.spec.ts:632` — *"the bar sits clear of the banner instead of under it"*).

## Follow-ups

- Decide whether the drawer should shrink while the cookie banner is up, as the commit bar does.
- Real-device iOS Safari pass: open the drawer with the address bar expanded and collapsed, and
  confirm the panel clears the home indicator.
- Still unaddressed: the panel has `overflow-hidden` and **no internal scroll container**, so
  content taller than the panel is clipped and unreachable. This change makes it strictly better,
  but a landscape phone could still clip. The safe fix is `overflow-y-auto` on the inner wrapper
  (`sidebar.tsx:276`), not the panel — the panel's `overflow-hidden` is what the `clip-path`
  animation relies on.
